# 프로토타입 통합 검수와 다음 작업 계획

## 현재 결론

`develop/prototype`에는 메인 대시보드, 장비 검색, 장비 통합 상세, 납품 일정 관리, 변경 신청 조회 화면과 Stub API 경계가 통합되어 있다. 모든 기능은 실제 DB 없이 일반화된 목업 데이터로 동작하며, 확정되지 않은 업무 상태와 처리 규칙은 화면 가정으로 분리했다.

GitHub Actions에서 타입, 린트, 단위·통합 테스트, Stub API 계약, 프로덕션 빌드, Chromium 1440×900 브라우저 시나리오를 PR마다 검사한다.

## 검수 중 발견하고 수정한 내용

1. 통합 상세 담당자명이 상단 사용자명과 요약에도 표시되어 단순 개수 검사가 불안정했다. 담당자 영역의 실제 표시 여부를 검증하도록 수정했다.
2. 납품 상태 필터의 한글 기반 HTML ID가 브라우저 접근성 조회에서 불안정했다. 고정 영문 ID와 레이블 연결을 적용했다.
3. GitHub Actions에 Chromium 설치와 Playwright 실행을 추가해 로컬 브라우저가 없는 환경에서도 화면 회귀를 차단했다.
4. 지연 규칙이 미확정인데 날짜로 자동 판정할 가능성을 제거하고, 명시적인 목업 플래그만 표시하도록 제한했다.

## 남아 있는 제약

- 실제 로그인, 역할별 권한, 변경 승인·반려, DB 저장은 구현하지 않았다.
- 품목 유형의 실제 DB 저장 위치와 공통코드는 미확정이다.
- 납품의 발주·입고·납품 단계와 지연 판정 규칙은 미확정이다.
- 변경 신청 상태값과 처리 순서는 프로토타입 가정이다.
- 장비 변경 이력 그래프는 아직 정적 시안만 있으며 실제 페이지는 후속 범위다.
- `react-router` 보안 권고는 현재 사용하지 않는 RSC API에 해당하지만 운영 전 호환성 검증과 업그레이드가 필요하다.

## 다음 권장 작업

1. 사용자 승인 후 현재 `develop/prototype`에서 `release/prototype-v2` 생성
2. 회사 시연 범위를 기준으로 release 브랜치의 메뉴와 진입 동선 최종 확인
3. 장비 변경 이력 그래프의 데이터 계약과 사업별 대체 관계 확인
4. 실제 백엔드 기술이 정해지면 Delivery·Change Request HTTP Adapter 구현
5. 역할별 조회·수정·승인 권한을 확인한 뒤 인증·인가 경계 설계

`main`은 1차 공개본으로 유지하며, release 브랜치는 사용자 승인 전 생성하지 않는다.
