# 1차 프로토타입 구조

## 1. 목적

메인 대시보드와 장비 검색 화면을 실제 DB 및 운영 API 없이 검증한다. 화면 코드를 목업 데이터에 직접 결합하지 않고 향후 API Adapter로 교체할 수 있도록 구성한다.

## 2. 소스 구조

```text
src/
├─ app/                  라우팅과 애플리케이션 진입점
├─ components/
│  ├─ common/            페이지 헤더, 카드, 상태 배지
│  └─ layout/            사이드바와 상단 헤더
├─ features/
│  └─ equipment-search/  검색·필터·정렬 규칙과 단위 테스트
├─ mocks/                일반화한 목업 Fixture
├─ pages/                대시보드와 장비 검색 페이지
├─ services/             교체 가능한 데이터 접근 인터페이스
├─ theme/                공통 디자인 토큰
├─ types/                화면과 서비스에서 사용하는 타입
└─ styles/               전역 스타일
```

## 3. 데이터 접근 경계

```text
Page
→ Service 인터페이스
→ 현재 Mock Adapter
→ Mock Fixture
```

페이지와 컴포넌트는 `src/mocks`를 직접 참조하지 않는다. 실제 API가 확정되면 Service 인터페이스를 유지하고 구현체만 HTTP Adapter로 교체한다.

## 4. ERD와 화면 조회 모델의 차이

ERD의 중심 관계는 다음과 같이 이해한다.

```text
Item
├─ 복수 계통
├─ 복수 정비 계단
├─ 복수 담당자 확장 가능
└─ Integrated_Info
   ├─ Business
   └─ 복수 Contract_Delivery
```

DB는 정규화된 여러 행으로 정보를 저장하지만 장비 검색 결과는 품목 하나당 한 행을 표시한다. 따라서 프론트 조회 모델은 다음을 배열로 받는다.

- 적용 사업
- 적용 기종
- 적용 계통
- 정비 계단
- 담당자
- 사업별 납품정보

목록에서는 대표값과 `외 N개`, `외 N명`을 표시하고 상세 패널에서 전체 내용을 보여준다.

## 5. 구현된 상호작용

### 메인 대시보드

- 통합 검색 후 장비 검색 화면 이동
- 주요 현황 카드 선택
- 목업 납품 계획·실적 차트
- 확인 업무, 최근 변경, 납품 임박 현황

### 장비 검색

- 품번·품명·용도 부분 일치 검색
- 기종·사업·계통·장비 구분·담당자·납지·상태 복합 필터
- 선택 조건 표시와 개별 삭제
- 필터 전체 초기화
- 모든 주요 열 정렬
- 페이지 이동
- 키보드로 검색 행 선택
- 선택 장비 상세 패널
- 로딩·빈 결과·오류 상태

## 6. 프로토타입 가정

- 대시보드 수치와 차트는 고정 목업값이다.
- 납품 단계와 지연 계산 규칙은 아직 구현하지 않는다.
- `정`·`부` 담당 구분은 확장성 확인을 위한 화면 속성이다.
- 업체 테이블의 실제 업무 명칭과 제조사·구매처 구분은 미확정이다.
- 사용 상태와 최근 변경일은 화면 검증용 값이다.
- 실제 API Endpoint, 인증, 권한, 오류 규격은 미확정이다.

## 7. 실제 API 전환 순서

1. 백엔드 조회 API 계약과 페이징 방식을 확정한다.
2. 화면 타입과 API DTO의 매핑 함수를 작성한다.
3. `dashboardService`, `equipmentService`의 Mock 구현을 HTTP 구현으로 교체한다.
4. 서버 검색·정렬·페이징 적용 범위를 확정한다.
5. 실제 상태 코드와 공통 코드 표시명을 연결한다.
6. 권한별 필드 노출과 오류 처리를 적용한다.
