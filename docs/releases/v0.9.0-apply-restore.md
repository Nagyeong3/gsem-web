# GSEM v0.9.0 적용·복원 가이드

## 범위와 선행 조건

기준은 `feature/main-workflow-page`의 `0376c62a4a487b0634c95b286053d97d0aed9b62`다. 승인된 장비 검색·지원장비 통합현황 구조를 유지하며 검색 실행, 필터 삭제, URL 상태, 컬럼 너비 저장을 안정화한다. 실제 인증·DB 쓰기·승인 기능을 추가하지 않는다.

이 ZIP은 완성된 Mock/API 프론트 빌드, 소스, Python 오프라인 wheel, npm 캐시, 복원용 Git bundle·변경 패치를 포함한다. 배포 시 프론트 재빌드는 필요 없다. Python 3.12 x64와 최신 Chrome/Edge는 대상 PC에 사전 설치해야 한다. 소스 재빌드에는 Node.js 24 x64와 npm 11이 필요하다. 런타임 설치 프로그램·브라우저 바이너리·Microsoft ODBC 드라이버·회사 데이터·자격 증명은 포함하지 않는다.

Python wheel은 Windows x64 CPython 3.12 및 Linux x64 CPython 3.12용으로 구분한다. Windows용 pyodbc 5.2.0 wheel도 포함하지만 SQL Server 연결에는 별도 ODBC Driver 17/18 및 승인된 접속 설정이 필요하다. Linux에서 오프라인 설치·재빌드를 검증했다. Windows 실행은 이 환경에서 검증하지 않았으므로 반입 후 검수해야 한다. 다른 CPU·Python 버전에는 이 wheel을 사용하지 않는다.

## 구성

- `frontend/mock`: DB/API 없이 실행하는 화면
- `frontend/api`: 동일 출처 `/api/v1` 호출용 화면
- `source`: 전체 소스·문서·테스트·기존 SQL 점검문
- `offline/wheels/linux`, `offline/wheels/windows`: Python 의존성
- `offline/npm-cache`: 잠금 파일에 대응하는 npm 캐시 (Linux/Windows x64 선택 패키지 포함)
- `recovery/history.bundle`: 기준과 안정화 커밋을 포함하는 Git 기록
- `recovery/v0.9.0.patch`: 기준 커밋 대비 변경분
- `manifest.json`: 버전·기준 커밋·릴리즈 커밋·파일별 SHA-256
- `검증-결과.md`: 실제 수행한 검증과 제한

## 적용 전 보존과 무결성 확인

1. 기존 서비스를 중지하고 설치 폴더 전체를 날짜가 있는 별도 폴더로 백업한다. 사용자 소스 변경, `.env` 등 접속 설정, 이미지 폴더, 실행 명령·포트·서비스 등록값을 별도로 보존한다. 백업 파일을 이 패키지에 합치거나 외부에 올리지 않는다.
2. ZIP을 기존 설치 폴더와 다른 새 버전 폴더에 푼다. 기존 폴더 위에 덮어쓰지 않는다.
3. 제공된 ZIP SHA-256과 반입 전 기록을 대조한다. PowerShell은 `Get-FileHash .\GSEM-v0.9.0-offline.zip -Algorithm SHA256`, Linux는 `sha256sum GSEM-v0.9.0-offline.zip`을 사용한다.
4. 압축 해제한 `GSEM-v0.9.0` 폴더에서 다음을 실행한다.

```text
python source/tools/verify-release.py .
```

해시 불일치·파일 누락이 있으면 적용을 중지하고 원본 ZIP을 다시 반입한다. 설치 후 생성된 `.venv`나 캐시는 manifest 대상이 아니다.

## Mock 화면 실행 (추가 패키지 설치 불필요)

패키지 루트에서 실행한다.

```text
python source/tools/serve-release.py --root frontend/mock --port 8080
```

대상 PC 브라우저에서 8080 포트를 열어 대시보드·장비 검색·통합현황을 확인한다. `/equipment`나 `/equipment-master` 직접 접속·새로고침도 확인한다. 이 서버는 로컬 검수용이다. 사내 공용 서비스는 승인된 IIS/Nginx 등의 웹 서버에 빌드 폴더를 배치하고 SPA fallback과 API reverse proxy를 설정한다. Python 검수 서버를 운영 서비스로 등록하지 않는다.

## API 화면 실행

패키지 루트의 첫 터미널에서 Windows PowerShell:

```powershell
python -m venv source/.venv
source/.venv/Scripts/python -m pip install --no-index --find-links offline/wheels/windows -r source/requirements-dev.txt
Set-Location source
.venv/Scripts/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 4010
```

Linux에서는 다음을 사용한다.

```bash
python -m venv source/.venv
source/.venv/bin/python -m pip install --no-index --find-links offline/wheels/linux -r source/requirements-dev.txt
cd source
.venv/bin/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 4010
```

두 번째 터미널은 패키지 루트에서:

```text
python source/tools/serve-release.py --root frontend/api --port 8080
```

`/health` 응답과 대시보드·장비 검색의 실제 HTTP 조회를 확인한다. 인메모리 FastAPI는 일반화된 JSON 데이터로 동작한다. API 빌드에서 통합현황은 SQL Server 전용 Endpoint를 사용하므로 DB 설정이 없으면 503·재시도 상태가 표시되는 것이 예상 동작이다. 통합현황 Mock UI 검수는 `frontend/mock`에서 수행한다. 나머지 인메모리 API가 성공해도 SQL Server 연결 성공으로 간주하지 않는다.

## SQL Server 별도 검증

실데이터 검증은 이 릴리즈의 자동 검사와 구분한다. 실제 테이블·권한·ODBC·서버 인증서·연결 정보가 없어 이 환경에서는 수행하지 않았다. `ApplicationIntent=ReadOnly`는 쓰기 권한 차단을 보장하지 않으므로 승인된 읽기 전용 DB 계정을 사용한다. 실제 접속 값은 안전한 로컬 환경변수 또는 기존 서버 설정에만 입력한다.

1. Windows Python 환경에 `--no-index --find-links offline/wheels/windows pyodbc==5.2.0`으로 pyodbc를 설치하고 ODBC 드라이버·비트 수를 확인한다.
2. 기존 설정 규약인 `GSEM_DATA_SOURCE`, `GSEM_DB_HOST`, `GSEM_DB_PORT`, `GSEM_DB_NAME`, `GSEM_DB_USER`, `GSEM_DB_PASSWORD`, `GSEM_DB_DRIVER`, `GSEM_DB_ENCRYPT`, `GSEM_DB_TRUST_SERVER_CERTIFICATE`를 승인된 값으로 설정한다. 이미지 조회는 `GSEM_IMAGE_DIR`도 필요하다. 이 릴리즈는 인증서 검증을 우회하는 새 설정을 추가하지 않는다. 운영 환경에서는 신뢰 체인과 암호화 정책을 별도 확인한다.
3. API를 재시작하고 통합현황 목록·사업·조달원·바이어 필터를 확인한다. 사업별 동일 품번의 행 분리, 전체 건수, 페이지 경계, 정렬 순서, 필터 조합과 빈 결과를 원본 SELECT와 대조한다.
4. `source/docs/equipment-master-data-quality.sql`의 SELECT를 최종 스키마와 대조한 뒤 SSMS에서 실행한다. 중복 Integrated_Info, 고아 관계, 중복 matchId, NULL·음수 수량·납지·날짜 누락, 날짜 역전, 다건 계약을 확인한다.
5. CSV 전체 필터 결과 수·UTF-8 BOM·Excel 수식 이스케이프, 이미지 경로·미등록 이미지, 연결 실패 시 503·재시도 동작을 확인한다.
6. 판정 날짜, 대상 DB 버전, 데이터 기준 시점, 조건별 기대·실제 건수, 담당자와 미해결 차이를 내부 검증표에 기록한다. 실제 데이터·화면 캡처를 공개 저장소에 올리지 않는다.

DB 데이터나 스키마를 변경하는 마이그레이션은 포함하지 않는다. 실DB 검증을 통과하기 전에는 운영 데이터 정합성·성능·접속 준비 완료로 판정하지 않는다.

## 소스 적용과 자동 검사

기존 개발본에 패치로 적용할 경우 작업 내용을 먼저 별도 커밋/백업하고 기준 커밋과 일치하는 깨끗한 작업 브랜치에서 다음을 실행한다.

```text
git apply --check recovery/v0.9.0.patch
git apply --index recovery/v0.9.0.patch
```

다른 기준에서는 충돌을 검토해야 하며 강제 덮어쓰기를 하지 않는다. 새 소스 작업 폴더가 필요하면 패키지의 `source`를 사용한다. Git 기록까지 복원하려면 새 빈 폴더에서 `git init`, `git fetch <패키지 경로>/recovery/history.bundle HEAD`, `git switch -c agent/v0.9.0-stabilization FETCH_HEAD`를 실행한다.

패키지 `source`에서 Linux:

```bash
npm ci --offline --cache ../offline/npm-cache --no-audit --no-fund
npm run typecheck
npm run lint
npm run lint:backend
npm run test
npm run test:contract
npm run test:backend
npm run build
```

Windows도 같은 npm 명령을 사용하며, Python은 앞 절의 `.venv`에 설치한다. 오프라인 npm 캐시는 Linux x64에서 검증했고 Windows x64 선택 패키지도 추가했다. Windows에서 캐시 누락이 확인되면 승인된 연결 환경에서 해당 잠금 버전 패키지를 보완한 뒤 재반입한다. 네트워크나 무결성 검증을 끄지 않는다.

브라우저 검사에는 설치된 Chromium 계열 실행 파일을 지정한다. PowerShell은 `$env:PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`에 대상 PC의 Chrome/Edge 경로를 설정하고 Linux는 아래처럼 실행한다. 전용 Playwright 브라우저 다운로드는 필수가 아니다.

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e -- --workers=2
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e:api -- --workers=2
```

두 E2E 명령은 순차 실행한다. 화면 캡처·추적은 `test-results` 아래에 생성되며 기존 기준 시안을 덮어쓰지 않는다.

## 유지보수자가 통합 ZIP을 다시 생성할 때

`npm run build:release`는 Mock/API를 각각 `dist/mock`, `dist/api`에 빌드하고 API 주소를 동일 출처 `/api/v1`로 고정한다. 빌드 모드를 섞지 않는다. 두 E2E 실행이 모두 종료된 뒤 빌드한다. 브라우저 검사 도중 같은 `dist`를 다시 빌드하지 않는다.

Python 3.12 x64로 각 플랫폼 의존성을 `pip download --only-binary=:all:`의 `--platform`/`--python-version` 옵션으로 준비한다. Windows에는 pyodbc 5.2.0도 추가한다. `input/wheels/linux`, `input/wheels/windows`, `input/evidence`에 준비하고 npm 캐시에도 잠금 버전 의존성을 채운다. 자동 검사와 오프라인 설치를 통과한 로그·화면 캡처만 evidence에 포함한다. 소스 변경을 커밋한 뒤 저장소 루트에서 실행한다.

```text
python tools/package-release.py --input <준비 폴더> --npm-cache <npm 캐시> --output <새 출력 폴더>
```

패키징 도구는 수정 중인 소스나 기존 출력 폴더를 덮어쓰지 않는다. 소스·Git 패치·복원 기록·빌드·오프라인 의존성·검증 증거와 파일별 해시를 묶고 ZIP CRC를 확인한다. ZIP을 새 폴더에 풀어 `verify-release.py`를 실행하고 오프라인 설치·로컬 실행을 다시 확인한 후 전달한다.

## 사용자가 확인할 변화

- 검색은 입력만으로 실행하지 않고 Enter 또는 검색 버튼으로 실행한다. 한글 IME 조합 중 Enter는 검색하지 않는다.
- 필터 삭제 버튼은 해당 조건만 해제하며 다른 조건·페이지 크기를 유지한다. 조건 변경 시 첫 페이지로 이동한다.
- 장비 검색의 조건·정렬·페이지 크기·선택 행, 통합현황의 조건·페이지·보기 방식은 URL에서 복원한다.
- 장비 검색과 통합현황의 엑셀형·최적화형 컬럼 너비는 이 브라우저의 localStorage에 각각 저장된다. 계정별 서버 저장은 아니다.
- 컬럼 우측 경계 드래그, 장비 검색·최적화형 손잡이에서 좌우 방향키, 엑셀형 헤더에서 좌우 방향키로 너비를 조절한다. 너비 초기화는 검색 조건 초기화와 별개다.
- Mock 편집·변경 신청 초안은 기존처럼 브라우저 메모리 전용이며 새로고침 시 사라진다. Mock 역할 선택은 실제 인증이 아니다.

## 복원과 되돌리기

1. 새 버전 서버를 중지한다.
2. 백업한 이전 버전 폴더와 기존 실행 명령·서비스 경로를 되살린다. 보존한 접속 설정·이미지 폴더를 기존 위치에 연결한다. DB 변경이 없으므로 이 릴리즈용 DB 롤백 SQL은 없다.
3. 이전 화면의 직접 접속·검색·통합현황과 API 상태를 재검증한다. 브라우저는 강력 새로고침으로 이전 정적 자산을 다시 읽는다.
4. 필요하면 각 화면의 컬럼 너비 초기화 버튼으로 새 너비 설정만 지운다. 개발자 도구에서는 `gsem:equipment-search:widths:v1`, `gsem:equipment-master:excel:widths:v1`, `gsem:equipment-master:optimized:widths:v1` 세 키만 제거한다. 전체 localStorage 삭제는 다른 설정에 영향을 주므로 하지 않는다.
5. 소스 변경은 깨끗한 기준에서 적용했던 패치라면 `git apply -R --check`로 역적용 가능성을 먼저 확인한다. 이후 사용자 변경이 있으면 백업 브랜치에서 비교·병합한다. 작업 폴더 강제 초기화는 하지 않는다.
