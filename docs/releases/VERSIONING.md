# GSEM 버전 관리 기준 (Semantic Versioning)

## 출시 단계
- 요구사항과 데이터 연동이 확정되지 않은 사내 검증본은 **프로토타입**이며 `0.MINOR.PATCH`로 표기한다.
- 정식 업무 운영을 승인하고 최초 정식 릴리스를 확정할 때 `1.0.0`을 사용한다.
- 사내 서버에 올렸다는 사실만으로 정식 출시로 보지 않는다.
- 버전 번호는 소급 재사용하지 않는다. `0.9.0`은 기존 개발 이력으로 남긴다.

## 번호 증가 규칙
- `0.MINOR.0`: 프로토타입 기능 범위·화면 구조의 의미 있는 변경 (예: 테이블 → 달력 미리보기).
- `0.MINOR.PATCH`: 같은 기능 범위에서 오류 수정·소규모 개선.
- 정식 출시 후 `MAJOR.MINOR.PATCH`는 SemVer 호환성 규칙을 따른다. 브레이킹 변경 시 MAJOR, 호환 기능 추가 시 MINOR, 호환 버그 수정 시 PATCH.

## 배포 기준
- 현재 1차 시범 배포: **GSEM 프로토타입 v0.10.0 (읽기 전용)**.
- 실제 배포 소스 기준 Git SHA: `88e9dd4608c07546f95bbc371d47631ae34c4e9c`.
- 대표 배포 브랜치: `release/v0.10.0-prototype`.
- 이전에 생성한 `release/v1.0.1-demo-readonly`은 당시의 작업 이력 확인을 위해 삭제하거나 재작성하지 않는다. 같은 소스 커밋에 붙인 과거 실험 명칭이며 정식 운영 1.x 출시를 뜻하지 않는다.
- `feature/main-workflow-page`는 후속 개발용으로 사용한다. 각 배포에 해당하는 릴리스 브랜치는 검증 커밋에 고정하고 변경이 있으면 새 버전을 만든다.
- 배포 기록에는 **표시 버전, 커밋 SHA, 적용 날짜, 데이터 적용 범위, 읽기/쓰기 여부**를 함께 남긴다.
- 기존 `package.json`의 `0.1.0` 표기는 초기 내부 패키지 버전이므로, 다음 패키징 시 사용자 표시 버전과 통일한다. 현재 운영 서버의 파일을 수정할 필요는 없다.
